## 系列骨架：Harness 的五个概念

| # | 概念 | 所在篇目 | 一句话 |
|---|------|----------|--------|
| 1 | 上下文窗口 | 上篇第一章 | 从 <1 万到 100 万，够用 + 定向读取比一味求长重要 |
| 2 | 记忆 Skills / Rules | 上篇第二章 | 定向工作流 vs 全程硬性约束，本质都是提示词 |
| 3 | 外部记忆与 RAG | 上篇第三章 | 长文本存成向量库，按需抽取，解决上下文装不下的问题 |
| 4 | 工具调用 | 中篇 | 模型输出 JSON Schema 调 API；前端包的准确率天花板催生了本地 Harness 工具 |
| 5 | Plan Mode 与自主循环 | 中篇 + 下篇 | Plan 限制只读不改；自主循环 = 一问多轮：搜索 → 改 → 验证 → 结束 |

主线逻辑：以前只能干 4–50 秒、一两分钟 → 现在能干好几周、解决复杂问题，变化来自这五个环节的串联。

## 1. 上下文窗口的演变（上篇）

- 早期 <1 万 token：GPT-3.5 之前，模型靠“喂什么生成什么”，问答对很短，上下文长度不重要。
- 到 6 万：开始有人想往上下文里装内容，但 20 万字小说仍装不下，更不用说几十万行代码的项目。
- Grok 走极端：一下干到 200 万上下文，但主讲人认为没意义——长 ≠ 聪明，实际能准确提取的只有约 60%，像背书一样会“失忆”；而且 200 万也解决不了“贷款式”一次性塞入的问题。
- Google 回调：256k（25.6 万，一下砍 10 倍）→ 50 万（4.6/4.7 可选）；主讲人推测 4.8 或 5.0 可能回到 100 万。
- 共识：50 万和 100 万是目前比较公认的够用区间；100 万是分水岭，因为模型已会定向索引和读取（先按关键词/字符串匹配定位文件，再定向读取），不需要一次性全读进来。
- 量级类比：100 万 token ≈ 2000 页 A4 纸写满（小四、500 字/页）≈ 红楼梦读一两遍。
- 另有实验型模型做到 500 万上下文（美国厂商），但其他质量很差。

## 2. 记忆：Skills 与 Rules（上篇）

- 场景：固定工作流（去固定网站扒帖子 → 总结 → 按模板写报告），每次都要重新发一遍指令 → 把流程固化成文件，模型接任务时先读文件 = 记忆。
- Skills：工程上的定向技能方案，只针对对应工作触发。例：Word 的 Skills，做 PPT 的任务时不会调。
- Rules：更强硬，全程包含在上下文交互里。例：默认英文返回 → Rules 要求一律简体中文返回。
- 本质：两者都是提示词，只是触发节点和适用范围不同。以后见到新概念也一样，万变不离其宗——都是发给模型的输入。
- 外部记忆 = 调用文件，也叫长期记忆；与之相对是内部记忆。

## 3. 外部记忆与 RAG（上篇）

- 痛点：法律法规（中/美/全球）成堆的 Word 文档，100 万上下文也装不下。
- 方案：把长文本以向量形式存进小数据库（向量库），需要时抽向量库而非抽文件——向量更贴近模型的使用方式。
- 适用：几千几万个 Word 统一扔进来做存储，按需调用。

## 4. 工具调用（中篇）

- 本质：模型写一个 JSON Schema（不用 Object，因为 Object 只规范格式、不固定输出值；Schema 才能完全限制住），调 API。
- 算力背景（主讲人讲述）：
  - 早期 ChatGPT 只有约 3MW（中型电厂 60MW，一个小商场级别）；现在约 6GW，并已在美国电网建设中锁定 17GW（仅 OpenAI）；Anthropic 锁定 10GW。
  - 30GW ≈ 1.3 个三峡的发电量；一个机柜（2 米高）≈ 50 张 5090 的算力，30GW 的机柜能铺满北京二环（德胜门骑到玄武门）。
  - 算力不足时工作只能迁移到用户端：早期网站上封装第三方前端包，模型再强也被前端包的能力卡住（比如只能做到 50% 编辑能力）。
- Anthropic 在工具调用上步子比 OpenAI 大：Sonnet 3.5 / Sonnet 4 时代打通很多库，但很快看到上限——Word / Excel 预览不正确、颜色字号改不对，都是前端包准确率的问题。
- 于是出现本地 Harness 工具：安装到本地的 Claude Code、豆包、WorkBuddy 等；但本地化又引入新的解析复杂度问题（中篇此处有省略：XML 结构讲解等）。
- 工具调用的上限催生了 Plan Mode。

## 5. Plan Mode（中篇）

- Plan / Ask / Debug 三种模式：都是限制模型不允许修改、只允许查看；Plan 专做规划，Debug 专找错，Ask 专问问题。
- 趋势：模型思考和自纠错能力趋近全局规划后，Plan 的意义在变小——以前四步（问 → To-Do → Plan → 改）变成边干边修，To-Do 和 Plan 合并后直接改。
- 早期 Cursor 的 Ask / Debug 模式现在也用得少了。

## 6. 自主循环（下篇）

- 对比：一问一答（问“华盛顿是谁” → 一次回答）vs 自主循环（DeepSeek 开联网思考后：先搜 18–20 个网页再回答，就是两步走）。
- 本质：模型有起有终，分批次调入；引擎按轮次驱动：先看项目内容（列文件）→ 定位问题文件（搜 Button 组件出现位置）→ 改（Replace String，逐行重写替换，如补分号）→ 回测验证 → 发 End 结束。
- 等待机制：模型自身不能等，引擎等。调一个“等待”工具，设定等待值（1 秒、10 秒、600 秒甚至几千秒），引擎计时器到时再回来检查（构建目录是否出现、终端是否终止）。
- 能力外溢：给内容或不给内容，让模型用 SVG 生成一整套动画、在前端逐帧渲染成完整动画片——主讲人称这是历史上从未有过的事；该方向最强的是“Claude 3.5”（见下“待核实”）。
